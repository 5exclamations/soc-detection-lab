# Detection limitations

**Of the lab itself**
- All data is synthetic and generated by the same author as the rules. Precision/recall here show the rules do what they were designed to do on this data; they are **not** estimates of production performance. Real traffic has noise, gaps and attacker behavior this generator does not model.
- Labels are scenario-level and assigned at generation time. One dataset (seed 1337, 3 days). Counts are small, so a single alert moves the percentages a lot.
- The Sigma evaluator is a subset (see `sigma.py`); rules are not portable to other backends without a field-mapping pipeline.
- ATT&CK mappings are "relevant to", and API enumeration has no exact technique.

**Of specific detections** (also listed per rule in the catalog)
- Known misses, measured: low-and-slow guessing (EVA-01) and distributed guessing across many IPs (EVA-02). Roadmap: per-account aggregate failures over hours, and per-account distinct-IP counts.
- Threshold rules can be evaded by staying just below the numbers; thresholds are public in this repo.
- Geo-based rule uses country only and trusts source-provided GeoIP.
- Admin/cloud rules only see what is logged: a disabled or tampered pipeline blinds them (SOC-CLOUD-001 detects API-level tampering only).
- Ticket checks test presence, not validity.
- No asset or identity context (criticality, on-call roster, HR data), no user baselining, no ML.
- Event time is trusted; the engine processes a sorted batch and does not handle late or out-of-order arrival as a streaming system would.
